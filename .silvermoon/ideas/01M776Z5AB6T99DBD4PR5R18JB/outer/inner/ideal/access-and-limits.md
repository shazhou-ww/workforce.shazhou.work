# 邀请授权与资源边界

本文补充 [构想](Idea.md)
的访问规则。以下是待评审产品设计，不表示当前平台已支持这些能力。

## 管理员引导

以部署环境中的稳定 GitHub 数字 ID 白名单指定初始管理员，复用现有管理员识别思路，不能使用可变用户名或“首个注册用户自动成为管理员”。在部署后台配置身份；网页第一版只管理用户资格，不任命其他管理员。

管理员不依赖普通邀请取得管理权限，以避免无法进入后台；但仍必须有可信的登录身份。管理员不能从用户管理列表直接浏览他人的统计邮箱、个人配置和看板。管理能力不自动等于跨用户内容访问权。

主页对管理员显示“用户管理”，对获准普通用户显示“我的统计”和“个人配置”。隐藏按钮只是展示，所有权限都由服务端执行。

## 按邮箱邀请与稳定身份绑定

1. 管理员输入邮箱，保存一条待领取邀请；不开放自助注册审批队列。
2. 用户通过现有登录入口认证。登录成功本身不授予统计服务。
3. 服务端取得可信的已验证邮箱，与有效邀请精确匹配，原子地领取并绑定稳定内部用户 ID 和登录提供商账号 ID；重复回调应幂等，不能让不同账号并发领取同一邀请。
4. 后续访问按稳定用户身份及当前资格判断，不把每次返回的邮箱作为资源主键。

邀请邮箱去除首尾空白并按平台约定统一小写；不擅自删除 `+tag`
或 Gmail 中的点，不做模糊匹配。邀请邮箱与主作者匹配邮箱是独立字段。

不同提供商的邮箱声明不能一概视为已验证。GitHub 公共资料邮箱可能为空；需获取有可信验证标记的邮箱，否则走额外邮箱验证。Google、Microsoft 等亦须明确其可信声明和租户策略，缺乏证明就不能领取邀请。不能相信用户编辑的资料、浏览器传入的邮箱或任意 JWT 自定义字段。

若使用邮件验证，应为短时有效、单次使用、受尝试频率限制的挑战；具体提供商、权限范围或邮件服务留待实施时验证，不在原型中假装已发送邮件。多个账号返回同一邮箱不能自动合并或新增登录绑定；第一版不开放跨提供商自助账号关联。已有绑定冲突须明确提示并由管理员核实。

## GitHub 连接与平台资格独立

GitHub
OAuth 用于确认个人主账号及按需发现组织，不授予平台使用资格。通过其他提供商登录的获邀用户需显式连接 GitHub，不以相同邮箱自动合并账号；GitHub 登录用户复用已有身份，缺少
`read:org` 时再申请组织读取权限，不索取宽泛的 `repo` 权限。

OAuth 状态绑定当前稳定用户和一次性回调上下文；组织 API 使用的凭据仅保存在服务端受保护的凭据存储，不返回浏览器、公开快照或日志。现有登录配置不意味着已经实现后台组织发现；具体安全存储、续期／失效与组织策略兼容性在实施阶段验证。用户 OAuth 连接不默认变成后台永久采集凭据，后台采集授权仍与登录会话分开设计。

连接主账号只证明该主账号身份，手动补充的历史作者账号或邮箱只是统计条件。组织列表只是授权可见的成员关系，不是仓库所有权或私有仓库访问许可。撤销 GitHub 授权后应停止依赖该令牌的 API 调用并提示重新连接，不静默清除原有统计配置。

## 资格状态与操作

| 状态       | 用户体验                           | 管理员操作                 |
| ---------- | ---------------------------------- | -------------------------- |
| 待领取邀请 | 已验证邮箱匹配后可领取             | 撤销；需要时重新邀请       |
| 正常用户   | 只可使用本人配置、任务与结果       | 停用                       |
| 已撤销邀请 | 不能再以该邀请领取                 | 重新邀请，不恢复旧领取凭据 |
| 已停用用户 | 明确显示停用；已有登录会话也无权限 | 恢复既有用户资格           |

停用用户与撤销未领取邀请是不同操作，必须二次确认并清楚说明影响。恢复只恢复资格，不自动改变其自动更新开关或立即启动采集。管理员自己不能在此列表停用自己的引导身份。

应保留操作者、时间、目标稳定身份和操作类型的受保护审计信息；不要在普通日志打印邮箱、令牌、邮件验证码或原始 OAuth 数据。第一版不要求自动发送邀请邮件，管理员可通过自己的渠道通知受邀者。

## 所有入口统一执行授权

个人配置、统计、任务进度、刷新、重试及后续自动调度，都必须校验当前资格与资源归属。未登录返回认证要求；未获邀、邮箱未验证或被停用返回清晰的访问受限信息；不能泄漏其他人的资源是否存在。

停用后不得继续分配新任务；排队任务取消，在途任务在安全检查点停止后续处理且不得发布新快照。不能仅靠登录时缓存的管理员或资格声明。已被下载的数据无法收回，界面不能声称停用可删除用户已保存的内容。

个人 API 和邮箱相关响应禁止公共缓存；快照即使在 KV 内也只能由校验身份与归属后的服务端读取。现有公开看板独立保留，不能让旧的公开 API 读到新用户个人快照。

## 邀请制之外的资源保障

管理员控制每人仓库上限、手动刷新冷却、首次历史采集预算、全局并发与定时频率。组织展开和显式纳入去重后的实际仓库范围也必须受限，不仅限制输入条数。

首次全历史初始化的成本需单独评估。超预算应明确阻止或等待调度，不得只抓一部分后伪装成完整结果。失败、等待限流和保留旧结果应分别可见。一个用户的任务锁、异常及发布不能阻塞其他用户的全部任务；平台排队与并发限制除外。

原型的“最多 50 个仓库、手动刷新间隔 15 分钟、每小时自动更新”仅用于解释 UX，不是确认的容量承诺。上线数值需根据预算与真实采集成本确认。

## 第一版明确不做

跨用户聚合、排行榜、团队管理、多方案、私有仓库、自助公开分享、网页管理员提权，以及要求用户提交个人访问令牌。
