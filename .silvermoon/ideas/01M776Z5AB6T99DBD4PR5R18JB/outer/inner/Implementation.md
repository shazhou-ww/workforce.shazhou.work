# Implementation

本阶段实现已接受构想的生产功能。用户已明确授权由主 Agent 审批全部阶段门限、组织 subagent 实施，并在验收后通过既有 GitHub
Actions 发布；此授权不替代逐项实现与验证证据。

实现结果与检查记录见 [验收证据](verification.md)。

## Steps

### I-S01: 建立身份与邀请授权边界

补齐可信邮箱验证、邀请领取、稳定用户身份和管理员检查；统一保护配置、结果、任务与定时入口，支持撤销和停用。主账号来自 GitHub
OAuth，连接、组织读取与平台资格独立，凭据只在服务端受保护保存；组织读取错误不得伪装成空列表。

### I-S02: 隔离个人配置与采集结果

将全局配置、状态、发布锁与快照演进为用户归属明确的资源，保留配置版本、失败重试和完整发布语义；使用保留既有数据的 D1 迁移，保留现有公开看板、原有仓库范围和定时采集。新增个人资源受实际仓库数量、刷新冷却及平台任务预算控制。

### I-S03: 实现个人与管理员操作界面

在既有视觉语言下实现首次配置、个人看板、邀请管理及访问受限状态，并增加直接覆盖新行为的测试。个人配置只用顶部按钮打开的模态面板，不新增侧边栏；包括只读主账号、组织勾选、仓库逐项添加移除、排除优先及历史身份补充。

## Acceptance criteria

### I-AC01: 授权与归属不可绕过

通过 API 与任务入口测试证明：未获邀或被停用用户不能读取或修改个人资源，用户不能跨归属访问；邮箱未验证不能领取邀请，已有会话不绕过停用。

### I-AC02: 统计行为与发布可靠性保持

用固定提交样本和迁移测试证明原有统计口径、公开看板、配置版本固定与失败保留旧快照行为不变；并验证配额与并发限制。

### I-AC03: 新增操作可完成且可理解

用界面测试与桌面、移动端人工检查覆盖首次配置、保存、刷新、邀请、撤销、停用和失败提示，运行仓库规定的 pnpm
check。组织授权回跳后直接定位到选择区域；空列表必须说明组织放行与个人授权的区别，并提供对应 GitHub 应用的组织访问入口。
