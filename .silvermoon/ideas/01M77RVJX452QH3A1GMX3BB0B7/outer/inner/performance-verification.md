- `collection.ts`：HEAD 未变的仓库走上述批次；变化或全量历史仍保留固定头、独立的比较及历史分页、原检查点名称、重试行为与安全重建规则。成员选择本身计入规划阶段，不通过改阶段名隐藏历史工作。候选快照计算保持原样，包括既有就绪与发布校验调用：达成本次目标不需要消除重复快照计算，也未引入大型 Workflow 载荷。
- 性能优化本身不新增迁移、第三方依赖、前端改动或额外服务，不提高并发或调整配额；最新主线已有的迁移与前端功能完整保留。个人 200 仓库上限、50,000 条历史提交预算、15 分钟冷却和全局并发四保持不变。新增失败状态不会以默认成功结果返回。

个人任务的不可变清单最多包含 200 个数字 ID，存放于既有 D1 检查点，而非通过 Workflow 返回值序列化。旧默认范围任务保留原来的仓库数量限制语义。

## 可复现的受控方法

```powershell
pnpm --filter @shazhou-work/workforce-contracts build
node apps\worker\scripts\benchmark-collection.js 1684ff2877d4a19c349c1579fbd794fcf07d2d12
```

脚本直接从固定 Git 版本提取三个基线源码文件，放入项目内单次运行使用的基线目录；其余未变化的依赖共用。旧、新采集器分别使用全新的 Node
SQLite 数据库，迁移、合成配置、作者身份、可达历史提交集与 GitHub 测试数据保持一致。提取目录在
`finally` 中清理。

验收负载为 70 个仓库，其中 68 个 HEAD 未变（97.14% 复用）、两个仓库增量更新，共新增 13 条提交；固定截止时间为
`2026-11-12T12:00:00.000Z`，fork 与默认分支相同，没有外部限流或重试等待。每仓库起始均缓存相同的 12 条合成提交，覆盖日统计、滚动窗口、年度边界，以及仅账号匹配、仅邮箱匹配和不匹配的作者；提交身份仍包含仓库 ID。初始化截止时间早一天，因此 HEAD 未变仍需重算移动窗口。验收样本包含三组独立的混合负载成对运行；另报告一组全复用参考和一组首次初始化参考，不将它们混入验收中位数。

**这是延迟模型，不是生产测量：**混合及全复用负载对每次 D1 API 调用注入名义 2
ms 延迟。Windows 定时器调度可能使实际等待显著增加，原始结果记录了实测累计等待。事务内各条 SQL 不单独注入调用延迟。首次采集单独使用零注入延迟对照。全部 GitHub 请求均命中进程内测试数据，不访问 GitHub；未创建生产用户或生产负载。

适配器分别记录 SQL 语句、D1 调用及事务批次数。成功回调数是该测试程序实际执行的回调数，不是 Cloudflare
Workflow 调度器的实测值。持久化的 `collection_attempts.active_ms`
保持原计时边界，包含实时门限检查、不包含自身指标写入。测试程序另外测量**包含**指标持久化的规划及聚合回调耗时，以及整次调用的墙钟耗时，防止将工作移出验收计时边界来制造收益。

本地无法取得生产 D1 读写行数、SQL 引擎执行／排队／网络拆解、Workflow 持久化延迟与 GraphQL
cost，这些值明确为未知，而不是零。SQL 与调用计数是可靠的回归证据；注入延迟下的计时不构成生产 SLA。
