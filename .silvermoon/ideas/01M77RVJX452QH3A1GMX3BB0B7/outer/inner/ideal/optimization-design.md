# 优化方向与验证约束

本文补充
[Idea](Idea.md)，是准备阶段建议，不锁定具体类、表结构或批次常量。实测来源见
[生产基线](research-baseline.md)。

## 优先级与收益判断

| 优先级 | 方向                               | 预期收益与必要约束                                                                                         |
| ------ | ---------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 第一   | 后台资格检查使用最小字段、合并查询 | 保留实时停用、管理员引导语义与任务归属，不读取展示资料；最终发布仍原子检查资格。不能缓存权限一小时换速度。 |
| 第二   | 未变化仓库批量规划与聚合           | 降低逐仓库 Workflow callback、D1 往返与固定写入；先从有界小批次验证，不将 200 仓库做成单个巨型事务。       |
| 第三   | 本轮不变量和候选快照复用           | 固定配置、作者邮箱 HMAC、窗口和已完成快照不反复计算；候选内容必须不可变，可重放且不超过持久化载荷限制。    |
| 第四   | 限流预算与共享公开历史复用         | 分别调查匿名组织发现配额，以及首次任务复用已完成历史的条件；不与本次热缓存路径收益混算，不绕过组织策略。   |

旧采集退役与公开投影由独立迁移工作处理。本 Idea 以其最新结果为实施基线，不重复拆入口，不将“少跑一份旧任务”的收益冒充批量化成果。

## 缓存命中快速路径的意图

```text
固定用户配置版本、截止时间和仓库 HEAD
        ↓
批量读取元数据与完整同步水位
        ↓
分流：未变化仓库 / 变化仓库 / 首次或重建仓库
        ↓
未变化仓库按批次重新计算本轮统计
变化历史保留独立固定 SHA、分页游标与重试检查点
        ↓
所有必需仓库完成 → 不可变候选快照 → 安全发布
```

这是目标处理边界，不要求另建服务、队列或数据库。优先复用现有查询、collector、Workflow 和 D1
batch；只有测量证实需要时才引入新机制。

### 不能省略的正确性

- HEAD 未变也需重新计算移动窗口。不能直接复制上轮总数：窗口边界、当日部分数据、年度首日和滚动 24 小时锚点都会变化。
- 作者配置变化必须重新匹配；缓存键不能只有仓库 ID 或 HEAD，还需区分相关配置版本、截止时间、可达历史代和统计口径。
- 每个批次保留可核验的成员集合、固定头与原子进度。重放不重复或漏算；不能先标 complete 再补统计。
- 停用、取消、配额和发布 fencing 保持有效。批次开始和边界的检查不能替代发布时的原子资格与所有权条件。
- force-push、分支切换、无法比较基准仍走安全重建；不以时间戳或已知 SHA 作为分页提前终止条件。
- 共享完整公开历史只复用已成功、可达性明确的代，不复用其他在途任务的暂存状态；需要协调并发写入与失效策略。不能直接把其他用户的私有统计结果当作公共缓存。

## 为什么不先增加并发

最新无等待样本仅 15 个 GitHub 请求，但规划与聚合已有 327.4 秒。先并发历史请求对主要瓶颈帮助有限，还可能加重 D1 排队、GitHub
secondary limits 与失败重试放大。

后续如需并发，应按凭据预算、API 实际耗时、GraphQL
cost 与 D1 写入能力设置有界上限。多个 GraphQL 子查询合成一个 HTTP 请求，不代表 cost 按同样比例下降。

## 验证方法与门槛

### 固定负载对照

使用可重放数据集：约 70 仓库、至少 95%
HEAD 未变、少量仓库增量更新；固定配置、提交集合、默认分支、截止时间、数据库内容与运行地区。旧实现与新实现各至少三次成对运行，隔离冷启动、历史初始化和 GitHub 限流。

验收指标为规划与聚合合计 callback 活跃耗时的中位数降低至少 70%。例如历史观测的 327.4 秒只能说明优化空间，不能直接拿异环境新结果低于 98.2 秒就宣布达标。正式基线应在最新迁移版本上重测。

同时报告：

- 整轮 wall time、各阶段活跃时间、外部等待和重试时间。
- D1 往返数与 SQL 语句数，二者分开；SQL rows
  read/written 和执行时间，在平台可取得时记录。
- Workflow 实际 callback／持久化批次数、性能记录成本。
- REST／GraphQL 请求数，凭据是否存在、rate limit 及可取得的 GraphQL
  cost；不记录令牌或请求正文。

计时边界变化必须说明，不能把工作移出计时段、合并阶段名称或停止记录性能就声称提速。全缓存命中与变化仓库路径分别报告，首次初始化不与其混合。

### 语义与可靠性对照

优化前后比较 30 天 daily、仓库明细、totals、365 天 yearly、rolling，以及公开投影使用的统计内容；固定截止时间后仅剔除允许变化的生成时间等元信息，不能忽略统计差异。

覆盖日期边界与窗口淘汰、作者账号和邮箱“或”匹配、空仓库、排除与仓库重命名、merge／回退可达历史；覆盖中途停用和取消、批次失败、Workflow 重放、旧结果保留及新旧任务发布顺序。

### 生产观察

不为评估而重复触发大量生产任务。优先利用自然调度的可比样本，注明仓库数量、reuse 比例、变化提交、其他并发负载和外部限流。权限不降级，保持每人 200 仓库及现有历史、冷却、并发预算，除非另获明确需求变更。

## 诊断改进与当前排除项

需要能安全区分 D1 执行、通信、排队或平台错误类别；若平台未提供细分信息就标未知，不能从
`_sendOrThrow` 栈推断 overload。诊断不打印邮箱、SQL 绑定值、凭据或私有配置。

不先引入缓存服务、数据库分片、无界并发或批量历史重构；不先删除已有 rolling 字段或改变统计口径来降低计算量。首次初始化与组织发现策略可作为后续收益项，在核心命中路径验证后再评估。
