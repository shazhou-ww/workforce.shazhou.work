# Deployment

用户已明确授权由主 Agent 审批全部阶段门限，并通过现有 GitHub
Actions 发布生产。仅在实现验收、主线同步与发布前检查完成后使用新的 Release 标签；不从本地直接部署。

## Steps

### D-S01: 确认上线配置与迁移保障

在上线前确认管理员稳定身份、邮箱验证能力、资源预算，以及现有公开看板归属、数据备份和迁移恢复路径。用户已针对 Actions 令牌缺少 D1 编辑权限的情况，明确选择使用现有授权 Cloudflare 连接先迁移 D1，再由 Actions 发布 Worker 与静态资源。迁移前取得 Time
Travel 书签，应用经过保留数据测试的迁移并校验外键和既有状态；迁移失败时不发布标签。

### D-S02: 按授权流程发布

仅在明确获得生产发布授权后，集成最新主线并通过检查，使用新 Release 标签触发现有 GitHub
Actions 部署流程，不从本地直发生产。

### D-S03: 验证真实邀请与个人隔离

使用经授权的管理员验证线上登录、个人入口与现有公开页面；用生产匿名请求检查受限 API。受邀、未受邀、邮箱缺失、停用及跨用户隔离由定向集成测试覆盖，不冒用其他用户登录，记录不含敏感数据的验证证据。

## Acceptance criteria

### D-AC01: 现有服务未被覆盖

通过迁移前后生产页面、API 与既有统计样本对照，证明原公开看板仍可访问且未被新用户结果覆盖。

### D-AC02: 邀请授权实际生效

线上管理员登录与匿名受限请求证明认证入口和服务端门禁实际生效；受邀、未受邀、缺失可信邮箱、已有会话停用及任务停止由自动化集成测试证明。无法控制的其他真实用户身份不伪造为线上验收证据。

### D-AC03: 发布与资源状态可核验

部署工作流成功，生产 API 和 UI 检查通过，并能从受保护的任务与配额信息确认资源限制生效，不暴露凭据或用户邮箱。
