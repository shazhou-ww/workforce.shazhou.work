## 源码已确认的行为

### 缓存只省掉历史网络请求

[collection.ts](../../../../../../apps/worker/src/collection.ts)
先按 owner 将元数据每 10 仓库合并 GraphQL 请求，再进入
`for (const original of repositories)` 串行循环。HEAD 未变时
`sync_mode = reuse`，跳过历史拉取，但仍执行逐仓库规划和聚合。

每个仓库至少有 `pin and plan`、`aggregate and advance watermark` 两个 Workflow
callback。界面约每 10 秒轮询进度，因而显示两三个仓库一跳；这个跳动不等于 GitHub 以两三个仓库为一批请求。

### 个人资格检查是重复往返热点

[platform.ts](../../../../../../apps/worker/src/platform.ts) 的
`assertPersonalActive` 调用完整 `platformAccess`，对于存在的用户读取：

1. 用户状态；
2. GitHub 登录身份，计算管理员资格；
3. GitHub 连接及用于展示的字段。

[collection.ts](../../../../../../apps/worker/src/collection.ts)
在每个实际 callback 前后各检查一次，开始前再读一次任务取消状态。仅 70 仓库的规划和聚合 140 次 callback，按当前调用结构就有约
`140 × (3 + 1 + 3) = 980`
条辅助读取，另有至少 140 次性能记录写入。此数字是源码推导，不是生产逐 SQL 跟踪计数。

检查还会创建新的 `CollectionStore`，其
[构造函数](../../../../../../apps/worker/src/collection-store.ts) 使用
`withSession("first-primary")`。这提示存在重复会话和主库往返成本，但尚未测量各查询的网络 RTT 或主库排队占比。

### 未变化仓库仍有固定本地工作

[collection-store.ts](../../../../../../apps/worker/src/collection-store.ts)：

- `plan` 读取后写入本轮计划，即使复用历史也创建相应检查点。
- `finishRepository`
  再次读取 run、计算邮箱 HMAC，再以 8 条 SQL 的 batch 合并历史成员、生成本轮提交匹配和日聚合、更新水位及完成状态等。
- `snapshot`
  在标记 ready 和实际发布两个 callback 中各构建一次，重复读取、年度与滚动统计。两次构建是已确认的重复计算，暂未证明其占总耗时的大头。
- 任务状态查询还分别读取 run、完成数、错误、等待及性能；与采集写入共用 D1。可以调查降低展示查询成本，但不能将前端更低频轮询当作核心优化成果。

## SQL 查询计划与平台约束

只读 `EXPLAIN QUERY PLAN` 对两类历史查询得到：

- 仓库窗口提交使用 `commits_date(repository_id, committed_at)`。
- 可达历史成员使用 `history_commits` 的覆盖主键索引。
- 年度查询的运行仓库范围使用 `run_repositories` 的主键。

因此目前没有证据支持“先补索引就能解决”。这些计划不等于实际扫描行数、执行时间或锁等待测量；优化前仍需看高频语句和 rows-read。

Cloudflare
[慢查询与批处理说明](https://developers.cloudflare.com/d1/observability/find-expensive-queries/)指出：连续小查询的独立 D1 往返也会造成延迟。[D1 限制说明](https://developers.cloudflare.com/d1/platform/limits/)指出单库串行处理查询，增加并发不保证增加吞吐。应用应先减少必要往返、检查 batch 与 SQL 计划，而不是默认高并发。

## 限流与读取失败的独立事实

- 组织发现可以使用未带 token 的公共目录客户端；其匿名额度与带凭据的 REST／GraphQL 配额不同。不能用设备
  `gh` 的余额证明 Worker 凭据或匿名目录没被限流。
- 18:34:37 前后，个人进度接口连续 503，同时有 D1 `_sendOrThrow`
  性能记录失败。Workflow 发布步骤发生过 `AggregateError`，随后重试成功并发布。
- 日志未保留足以区分 overload、超时、连接或其他内部错误的安全分类，不能断言是数据库过载。
- 前端在短重试耗尽后停止轮询的问题已于 `Release-261112-8`
  修复；这是故障恢复，不是采集性能优化，不应计入本 Idea 的提速收益。

## 尚待验证，不应当作结论

权限辅助查询的实际网络／执行／排队耗时、全量扫描与写入量、性能记录成本、Workflow 持久化开销，以及退役旧任务后的实际资源改善均需进一步测量。暂未承诺任何固定秒数的整轮 SLA，也未完成 70% 优化目标。
